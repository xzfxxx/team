# 编排细则（按需加载）

> 本文件是 `SKILL.md` 的展开件：阶段细则、规模表、进度表、汇报格式、补充逻辑、错误恢复、DoD、报告模板。
> **只在真正进入执行阶段时读**；首轮判断不需要它。

---

## 1. 阶段细则

### Phase 3 需求澄清（模板含产品经理时）

1. 复述需求要点 + 边界 + 非功能要求（性能/权限/兼容）。
2. 列出**待确认问题**，一次问完（别一问一停）；给默认建议，方便用户只回"按你说的"。
3. 用户确认后才进规划。用户不回 → 按建议默认值推进，并在报告里标注假设。

### Phase 4 流程规划

架构师（或主 agent 代行）输出四块，给用户确认**一次**：

```
## 任务分析
独立任务：A（…）、B（…）
依赖任务：C（依赖 A）→ 等 A 完成
## 工作流
模板：standard-dev ｜ 或 新规划：自定义（步骤序列）
## 小组编排
第一波（并行）：A + B   角色：开发×2、质量×1
写域：A→src/a/**  B→src/b/**  （无重叠，可并行）
预算：角色 5 个 / 轮次 3 / 预计墙钟 60min
## 风险与边界
不可并行点、外部依赖、需要用户提供的信息
```

确认后按此执行。规划中途要改 → 停下来重新确认，不要边跑边改。

### Phase 5 执行

- 一个步骤 = 一个角色 + 一个明确任务 + 产物契约 + 写域。
- 派活时**不写"你自己看着办"**：给输入、给产物格式、给验收标准。
- 子代理之间不直接协调；需要协商 → 各回主 agent，由主 agent 决策后转达（DSH 的 agent-team 插件除外，它允许点对点发消息）。

### Phase 6 验收与修复

1. 收开发产物 → 派 QA（只读）→ 收问题清单（带证据）。
2. 清单原样转给**同一个**开发子代理（不要改写、不要删减，避免电话游戏）。
3. 修复完成 → 同一 QA 复审（它知道第一轮结论）。
4. 通过或触发退出阀。

### Phase 7 报告

- 主 agent 汇总；正式文档交文档工程师。
- 报告必须能独立看懂：不需要读者回头翻会话。

## 2. 规模表

| 独立任务数 | 角色实例 | 说明 |
|-----------|---------|------|
| 1 | 3（PM/架构 + 开发 + 质量） | 推荐；测试按需加第 4 个；数据层模板固定 +1 数据库 |
| 2 | 5 | 推荐；PM/架构/质量可跨任务复用 |
| 3 | 7 | 上限；再拆就分波次 |

- 角色实例 = 实际 spawn 的**不同子代理数**，不是"岗位数"。
- 超过 3 条独立任务 → 先压缩合并，或分波次（第一波 ≤3 条）。
- 并发受平台限制：DSH 默认 `maxActiveSubagents=8`，超了直接报 `ACTIVATION_LIMIT_REACHED`，不会排队。

## 3. 汇报与交接

### 3.1 子代理的最终回复（自包含）

```
## 结论
一句话：完成 / 部分完成 / 未完成（原因）
## 证据
- 改动：path/a.ts:12-40、path/b.tsx:3-18
- 验证：`pnpm test order` → 12 passed（贴关键输出）
## 未决项
- 🟡 path/c.ts:77 缺少空值兜底，未修（需确认是否在本次范围）
```

规则：
- 子代理**没有** `log()` 工具（那是 workflow 宿主函数）；进度用 `send_message` 发主 agent，正文 ≤200 字。
- 主 agent 对用户的**结论**近原文转述；只对内部协调信息做浓缩。
- 面向用户的最终结论**不能由子 agent 直接发**（它们没有对用户说话的通道），所以"结构化交接"是唯一可靠方式。

### 3.2 补充逻辑（4 个场景）

任何阶段发现要加逻辑，**先停、确认、再动**：

| 场景 | 做法 |
|------|------|
| 需求/规划阶段发现遗漏 | 列点问用户 → 更新规划 → 重新确认 |
| 开发中发现缺逻辑 | 开发汇报（附位置与影响）→ 主 agent 转述 → 确认后更新任务 prompt |
| 验收发现缺逻辑 | 写进问题清单 → 修复时明确写"新增逻辑"→ 单独复审 |
| 报告后发现要补 | 评估影响面 → 新开发补 → 单独验收 → 更新报告 |

汇报格式：

```
**发现位置**：path/file.ts:120 或 Phase 5
**补充内容**：……
**原因**：……
**是否影响已完成部分**：是 / 否（影响哪些）
```

## 4. 错误恢复与哨兵

| 失败类型 | 处理 |
|----------|------|
| 编译/构建失败 | 同一开发修，附完整错误输出 |
| 测试失败 | 同一开发修，附失败用例 + 堆栈 |
| 超时/无响应 | 拆小粒度重派；仍无响应→判定子代理不可用 |
| 连续失败 2 次 | 停下汇报用户，请求介入 |
| 子代理工具不可用 | 主 agent 接管收尾，显式声明退出团队模式 |

哨兵（任一触发就停）：

- **卡死**：某阶段连续 2 轮无新增产出（修复不收敛、讨论原地打转）→ 拆任务或换方案。
- **顺从**：两个 QA 结论高度一致但都拿不出各自证据，或互相引用对方结论 → 作废重审（按 6.5 盲审）。
- **跑偏**：队友交付物与目标不符（改了不该改的文件、答了别的问题）→ 立即中断，对齐目标后再派。
- **证据缺失**：QA 报告无 `path:line` 或无命令输出 → 打回，不计入轮数。

## 5. 交叉评审（盲审版）

只在打分项 3 或 4 命中时启用，成本 = 2× 质量工程师。**用文件化的隔离模板，不要临时手写 prompt**：

- QA-A → `prompts/blind-qa-a.md`（需求覆盖 + 变更安全）
- QA-B → `prompts/blind-qa-b.md`（健壮性 + 安全 + 数据/性能）

1. 两个子代理**并行启动**（同一条消息里两次派发，或同一个 workflow 里两个 `agent()`），避免 B 在 A 之后启动时被主 agent"顺口"补料。
2. 填 B 的模板时只放：仓库根、需求、diff、可用命令。**A 的清单、条数、id、"A 已发现"这类提示一律不写**；B 的模板里也没有对应占位符。
3. QA-A 只交清单 + 证据（模板已要求不给结论）；QA-B 同样。
4. 主 agent 合并：相同问题合并；冲突项用**可复现性**裁决（能跑出失败的一方胜）；都不可复现 → 标「争议」交用户。
5. 重合率 = 交集 / 并集；<30% 说明至少一方漏检严重 → 加第三审或人工复核。
6. 任一份输出带 `LEAK:` 行 → 该轮盲审作废，重派。

禁止事项：让 B 先看 A 的结论；用自报置信度加权；用多数票压掉有证据的少数意见。

## 6. 完成定义（DoD）

一个任务算完成，需要**同时**满足：

- 验收清单无 🔴 项；🟡 项已记录并给出后续处理方式；
- 声明的测试命令实际跑过，输出可见（不是"应该能过"）；
- 改动只落在写域内，没有顺手改别人的文件；
- `contracts/` 里的产物与最终代码一致（无过期文档）；
- 报告里的每个"已完成"都有位置可查。

部分完成也必须写清：哪些没做、为什么、需要什么才能继续。

## 7. 最终报告模板

```
## 团队协作 - 最终报告
**平台**：DSH ｜ **模板**：standard-dev ｜ **角色**：5 ｜ **轮次**：2/3 ｜ **墙钟**：~50min
**概览**：2 个任务，成功 2，失败 0

### 任务 1 - 订单查询优化
**结论**：已完成
**改动**：[OrderMapper.xml](src/main/resources/mapper/OrderMapper.xml):45-80、
         [OrderService.java](src/main/java/.../OrderService.java):120-168
**验证**：`mvn -Dtest=OrderServiceTest test` → 14 passed
**遗留**：🟡 [OrderMapper.xml:66](...) 未加索引提示，已记录（非本次范围）

### 任务 2 - …
### 成本与结论
- 实际角色 5 个 / 轮次 2 / 未触发退出阀
- 本次团队相比单 agent 的收益判断：并行拆了 2 条线，隔离了验收；若重做会改为单 agent（理由）
```

最后一行"是否值得"是给下一次决策留的依据——没有它就永远学不到团队何时划算。
